# 復旧とフラグファイル

このガイドでは、緊急停止、ローカルデータベースの復旧、および意図的なリモート再構築について説明します。これらは通常の同期操作ではありません。

> [!IMPORTANT]
> 復旧を始める前に、利用可能なすべてのVaultをバックアップしてください。中央リモートを使用している場合は、そのデータベースまたはバケットもバックアップします。正しいデータを持つコピーを決めるまで、ほかのLiveSyncデバイスを停止または一時停止してください。

Obsidianが正常に起動しなくても、復旧を諦める必要はありません。Obsidianを閉じた状態で、OSのファイルマネージャーを使ってフラグファイルを作成または削除できます。通常のLiveSync起動処理がデータベースや同期を開始する前に介入するための、サポートされた唯一の方法です。

## 最初に正しいデータを持つコピーを決める

状況に合う、最も破壊性の低い操作を選んでください。

- どのデータが正しいか不明な場合は、`redflag.md`ですべての処理を停止し、各コピーを保全してから調査します。
- 中央リモートが正常で、それを正とする場合は、**このデバイスの同期状態をリセット**または`flag_fetch.md`を使用します。
- このデバイスのVaultが正常で、破損または不要な中央リモートを置き換える場合は、**このデバイスのファイルでサーバーデータを上書き**または`flag_rebuild.md`を使用します。
- Vaultとローカルデータベースがどちらも正常で、未使用ストレージだけが問題の場合は、ガベージコレクションが適切なことがあります。破損したデータベースを修復する操作ではありません。

停止したCouchDBやオブジェクトストレージを診断する代わりに、同期方式を切り替えたり、P2Pを有効化したり、ガベージコレクションを実行したりしないでください。

## 診断前に停止する

Obsidianを完全に終了し、Vaultのルートに`redflag.md`という名前の空ファイルまたは空ディレクトリを作成します。次回の起動時、LiveSyncは通常のデータベース、ファイル監視、および同期処理を始める前に緊急停止状態へ入ります。

停止中に次を行います。

1. Vaultと、利用可能なリモートデータをバックアップします。
2. 目的のファイルがどのデバイスまたはリモートにあるか確認します。
3. 特定できた設定またはストレージの問題だけを修正します。
4. `redflag.md`を削除します。
5. Obsidianを起動し、`Hatch` → `緊急停止スイッチ`に残る停止設定を確認します。

このフラグは意図的にファイルログを有効化するため、性能へ影響することがあります。緊急事態の内容を把握したら削除してください。

## 競合または不一致のあるファイルを復旧する

少数の既知ファイルに、競合、不足チャンク、または現在のVaultファイルとローカルLiveSyncデータベースとの差異がある場合に使用します。この調査はデバイス内だけで行われます。リモートデータベースへ問い合わせたり、別のデバイスに同じチャンクがあることを証明したりはしません。

`Hatch`の復旧操作は、影響の小さい順に並んでいます。チャンク設定とファイル内容を変えずに**現在のVaultファイルのチャンクを再作成**しても、同じチャンクが生成され、リビジョンツリーは変わりません。続く**競合とファイル／データベースの差異を調査**では、個々のリビジョンを対象に操作できます。**すべての競合ファイルを新しい方で解決**は更新日時に基づいて一括処理し、それ以外の有効なバージョンをすべて論理削除するため、最後に使用します。

1. 対象ファイルの編集を止め、参加デバイスのレプリケーションを一時停止し、読み取れる各バージョンを別に保存します。
2. 別のデバイスまたはバックアップに目的の内容がある場合は、リビジョンを変更する前に保全します。
3. 現在のVaultファイルを読み取れる場合は、**現在のチャンクを再作成**を選択します。現在のVault内容から作れるチャンクだけを復元できます。読み取れない履歴または競合リビジョンだけに存在する内容は復元できません。
4. **競合とファイル／データベースの差異を調査** → **調査を開始**を選択します。
5. データベースの採用リビジョン、すべての競合リビジョン、および読み取れない共通の祖先を個別に確認します。リビジョンID、`Δsize`、`Δtime`、およびチャンクの有無は診断材料であり、正しい内容を自動的に決めるものではありません。
6. 対象リビジョンのレンチメニューを使用します。
   - **Vaultと比較**：読み取れるテキストを読み取り専用で比較します。
   - **このリビジョンをVaultへ適用**：Vaultファイルを、読み取れるデータベースリビジョンで置き換えます。
   - **このリビジョンをVaultのバージョンとして記録**：子リビジョンを作らず、バイト単位で一致することを記録します。
   - **Vaultファイルをこのリビジョンの子として保存**：現在のVault内容を選択したブランチ上に保存します。
   - **リビジョンの読み込みを再試行**：リビジョンツリーを変えず、設定済みの方法でチャンク取得を再試行します。
   - **論理削除をVaultへ適用**、**このブランチを破棄**、および**読み込めないリビジョンを破棄**は破壊的な判断です。必要な可能性があるすべてのバージョンを保全してから使用してください。
7. チャンクを復元した場合は正常な取得元を同期し、再度調査します。目的の競合または差異が消えたことを確認してから通常の編集を再開します。

Vaultファイルが存在せず、採用リビジョンが論理削除なら、両者はすでに一致しています。別の有効なブランチがない限り、修復カードは表示されません。多数の無関係なファイルが報告される場合や、ローカルデータベース自体が不完全または破損している場合は、ファイル単位の復旧を止め、信頼できるリモートから[このデバイスの同期状態をリセット](#このデバイスの同期状態をリセット)してください。中央リモートを正しいVaultから再構築する必要がある場合は、[このデバイスのファイルでサーバーデータを上書き](#このデバイスのファイルでサーバーデータを上書き)します。

## このデバイスの同期状態をリセット

リモートのコピーは信頼できるものの、このデバイスのローカルLiveSyncデータベースが不完全、破損、または不整合になった場合に使用します。

読みやすいフラグ名は`flag_fetch.md`です。従来名の`redflag3.md`も引き続き使用できます。

次回の起動時、LiveSyncは次の順で処理します。

1. 通常の起動処理を一時停止します。
2. 複数のリモートプロファイルがある場合は、使用するリモートを確認します。
3. 既存のVaultファイルをどう扱うか確認します。
4. ローカルLiveSyncデータベースを破棄し、選択したリモートから再構築します。
5. 予定された操作が完了するか、安全にキャンセルされるまで通常動作を再開しません。

P2Pでは、取得元ピアがオンラインで、検出され、`P2P再構築`で選択されている必要があります。空のシグナリングルームを開くだけでは取得は完了しません。ピアを選択せず再構築ダイアログを閉じると失敗として扱われ、ローカルデータベースが復旧したことにはなりません。

未同期のローカル作業があるVaultで実行する前に、[高速セットアップガイド](tips/fast-setup_ja.md)を確認してください。

## このデバイスのファイルでサーバーデータを上書き

このデバイスのVaultが正しいコピーで、中央リモートをその内容から再構築する場合にのみ使用します。

読みやすいフラグ名は`flag_rebuild.md`です。従来名の`redflag2.md`も引き続き使用できます。

CouchDBとオブジェクトストレージでは、選択したリモートの状態を破壊する操作です。ほかのデバイスに、正しいVaultにはないリビジョンまたはファイルが残っている可能性があります。新しいリモートを検証するまでそれらのデバイスを停止し、検証後に新しいリモートからリセットしてください。

P2P専用構成には上書き対象となる中央リモートデータベースがありません。最初のデバイスを準備する操作では、そのVaultからローカルLiveSyncデータベースだけを再構築します。

## ガベージコレクションは再構築ではない

ガベージコレクションは、現在のデータベースとリビジョンモデルを維持したまま、参照されていないチャンクを削除します。次の条件をすべて満たす場合だけ使用してください。

- Vaultが正常である。
- ローカルLiveSyncデータベースが正常である。
- 関係するすべてのデバイスが同期済みである。
- 残っている履歴と削除状態を理解している。

削除済み文書、墓標、有効な競合、および保持されるメタデータにも容量が必要です。有効な競合ブランチは確認に必要なチャンクを保護しますが、通常の上書き済みリビジョンは以前のチャンクを保護しません。そのため、ガベージコレクションによって古い内容が読み取れなくなる場合があり、リモートが最小容量になる保証もありません。実行前に[ガベージコレクションV3仕様](specs_garbage_collection.md)を確認してください。

再構築は別の操作です。選択した正しい状態からデータベースを作り直すため、不要な履歴の削除や破損したリモートの修復には、より確実です。一方で影響も大きく、ほかの場所だけに存在する変更を失う可能性があります。

## フラグファイル一覧

選択した操作に必要なフラグだけを作成してください。

| Vaultルートのファイル | 効果 |
| --- | --- |
| `redflag.md` | 診断のため通常のLiveSync処理を停止します。手動で削除するまで残ります。 |
| `flag_fetch.md`または`redflag3.md` | 選択したリモートから**このデバイスの同期状態をリセット**するよう予約します。 |
| `flag_rebuild.md`または`redflag2.md` | **このデバイスのファイルでサーバーデータを上書き**するよう予約します。中央リモートがないP2Pでは、ローカルP2P準備を行います。 |

フラグファイル自体は同期対象外です。取得と再構築のフラグは、完了またはキャンセル後に予定処理から削除されます。`redflag.md`は手動で解除する緊急停止です。

## 警告が消えない場合

復旧ダイアログを閉じてもLiveSyncが緊急停止中と表示する場合は、次を確認します。

1. Obsidianを完全に終了します。
2. Vaultルートに上表のファイル名が残っていないか確認します。
3. 目的の操作が完了または中止済みのフラグだけを削除します。
4. Obsidianを再起動します。
5. `Hatch` → `緊急停止スイッチ`で、ファイル監視またはデータベース反映が停止したままになっていないか確認します。

正しいコピーをまだ判断できない場合は同期を停止したままにし、データベースを再度変更する前に[完全なレポート](troubleshooting_ja.md#レポートを収集)を収集してください。
